Poorman does not have its own settings for headers or authentication.
Anything you write after the path is passed straight to https://curl.se/docs/manpage.html[curl], so if you can do it with curl, you can do it with Poorman.

There are two places to put an option:

[cols="1,2,2", options="header"]
|===
| Where | Effect | Use it for

| `CurlOptionGlobal <option...>` +
(in `_env.sh`, or near the top of a script)
| Applies to every request *after* that line.
| Things every request needs: auth, `Accept` header, `--location`.

| `CurlOptionOnce <option...>` +
(right above one request)
| Applies to the next request only.
| A one-off header or different credentials for a single request.

|===

You can also put options on the request line itself:

[source,sh]
----
GET /users/1 --header 'X-Debug: 1'
----

In a collection, `CurlOptionGlobal` lines go in `collections/<name>/_env.sh`, so all requests in that collection share them.
In a single-file script (like `sample.sh`), put them above your requests.

== Basic auth (username and password)

[source,sh]
----
CurlOptionGlobal --user 'alice:s3cret'
----

curl turns this into an `Authorization: Basic ...` header for you.
Only the first `:` separates the username from the password, so the password may contain colons.

== Bearer token

[source,sh]
----
CurlOptionGlobal --oauth2-bearer 'eyJhbGciOi...'
----

This sends `Authorization: Bearer eyJhbGciOi...`.
The equivalent, written as a plain header:

[source,sh]
----
CurlOptionGlobal --header 'Authorization: Bearer eyJhbGciOi...'
----

== API key

Most APIs want the key in a header.
Check the API's docs for the header name:

[source,sh]
----
CurlOptionGlobal --header 'X-API-Key: abc123'
----

== Other common headers

[source,sh]
----
CurlOptionGlobal --header 'Accept: application/json'
CurlOptionGlobal --header 'X-Request-Source: poorman'   # add as many as you like
----

`--json '...'` (used in the `POST` examples) already sets `Content-Type: application/json` and `Accept: application/json`, so you rarely need to add them yourself.

== Other handy options

[cols="1,2", options="header"]
|===
| Option | Meaning

| `--location`
| Follow redirects.

| `--max-time 10`
| Give up after 10 seconds.

| `--verbose`
| Show the full request and response headers (useful when debugging).

| `--cookie 'session=abc'`
| Send a cookie.

| `--insecure`
| Skip TLS certificate checks. Only use on a local or test server.

|===

Run `curl --help all` or `man curl` for the full list.

== Self-signed or internal HTTPS servers (TLS errors)

curl checks that the server's certificate is trusted *and* that its name matches the address you used.
Internal servers often fail one or both, with errors like `curl: (60) SSL certificate problem` or `certificate subject name 'x' does not match target hostname '192.168.0.10'`.

*Quick, for a trusted test server only:* skip the check.

[source,sh]
----
CurlOptionGlobal --insecure
----

*Proper fix:* use the name on the certificate, map it to the IP, and trust the certificate.

. Find the name: `curl -vk https://192.168.0.10/` and read the `subject:` (CN) and `subjectAltName` lines.
. Save the certificate into the collection folder:
+
[source,sh]
----
openssl s_client -connect 192.168.0.10:443 </dev/null | openssl x509 > collections/jp/server.crt
----
. In `_env.sh`:
+
[source,sh]
----
BASE_URL=https://the-cert-name/some/path
CurlOptionGlobal --resolve the-cert-name:443:192.168.0.10 # <1>
CurlOptionGlobal --cacert "$COLLECTION_DIR/server.crt" # <2>
----
<1> `name:port:IP`. Requests to `the-cert-name` go to that IP, so the name check passes.
<2> Trusts that certificate. Relative paths are resolved from where you run `run.sh`, not from the request file, so use `$COLLECTION_DIR` (or an absolute path).

`--cacert` alone does not fix a name mismatch, and `--resolve` alone does not fix an untrusted (self-signed) certificate. A self-signed server usually needs both.

== Quoting tips

* Use single quotes (`'...'`) for fixed text, because the shell leaves it alone.
* Use double quotes (`"..."`) when the value contains a variable, such as `"$TOKEN"`.
* Always quote values that contain spaces, so the header below stays one argument:
+
[source,sh]
----
CurlOptionGlobal --header 'X-Greeting: hello world'
----

== Keeping secrets out of git

Do not commit real passwords or tokens.
A simple pattern is to keep them in a separate file that git ignores, and refer to them by variable name.

. Create `collections/jp/_secrets.sh` (the name is only a convention) and add `collections/*/_secrets.sh` to your `.gitignore`:
+
[source,sh]
----
TOKEN='eyJhbGciOi...'
----
. Load it in `collections/jp/_env.sh`, before the option that uses it:
+
[source,sh]
----
. "$COLLECTION_DIR/_secrets.sh" # <1>
CurlOptionGlobal --oauth2-bearer "$TOKEN" # <2>
----
<1> `$COLLECTION_DIR` is set by every generated request file to the collection's folder, so this works at any folder depth. (Request files made before this was added lack it; add a `COLLECTION_DIR=...` line above the `_env.sh` line.)
<2> Double quotes, so the shell fills in the value.

A simpler alternative is to pass it from the command line:

[source,sh]
----
TOKEN='eyJhbGciOi...' ./run.sh jp
----

with `CurlOptionGlobal --oauth2-bearer "$TOKEN"` in `_env.sh`.

[WARNING]
====
* A snapshot saves the status, timing, a few response headers and the body, but also the full URL. Do not put tokens in the query string (`?api_key=...`), or they end up in your script. Send them in a header instead.
* `DRY_RUN=1` / `./run.sh -n` prints the full curl command, including your credentials. Do not paste its output into chat or tickets.
====
